# Project Ash Planning Charter

## Purpose
This document defines how Project Ash will be planned and governed before any implementation starts.

## Core Rule
No coding, automation scripting, UI building, or environment setup will begin until the planning documents are reviewed and approved.

## Vision
Build a local AI desktop assistant that understands natural language and performs practical computer tasks with speed, reliability, and safety.

## Planning Objectives
- Translate vision into a concrete product scope.
- Define a realistic first release (MVP).
- Design a secure and modular architecture.
- Document risks, assumptions, and constraints.
- Define measurable success criteria.

## Guiding Principles
- Local-first by default, cloud optional.
- Safety and user control over autonomy.
- Reliable execution over flashy behavior.
- Clear observability: every action should be explainable.
- Incremental scope expansion through milestones.

## Constraints
- Primary target platform: Windows desktop.
- Initial operator: single user (personal assistant).
- Budget-conscious design: avoid unnecessary infrastructure.
- Privacy-sensitive tasks should remain on-device whenever possible.

## Definition Of Planning Complete
Planning is complete when all of the following are approved:
- Product requirements are frozen for MVP.
- System architecture is documented with boundaries and interfaces.
- Roadmap includes milestones, acceptance criteria, and dependencies.
- Safety, privacy, and risk controls are documented.
- Delivery workflow for implementation phase is documented.

## Approval Checkpoint
When planning is complete, implementation can start only after an explicit approval decision.

## Immediate Non-Goals During Planning
- Writing application code.
- Running installers or dependency setup.
- Building prototypes.
- Performing system-level automation tests.
